# Client-side promise caching for meta/list Supabase fetches

This change adds a small, Supabase-free cache mechanism (`lib/api/cache.ts`) and wires it into the four heavy "list the whole table" fetches that back revisited views: active-checks meta (`getAccuracyChecksMeta`, "M"), deleted-checks meta (`getDeletedAccuracyChecksMeta`, "D"), the global dispute list (`getAllDisputes`, "GD"), and open-dispute counts (`getOpenDisputeCounts`, "OC"). Each fetch body is hoisted verbatim into a private `fetch*` declaration and the public getter returns a module-level cached promise; every mutation that can make a cache stale calls the matching `invalidate*`. The acceptance bar is behavior preservation, and the only correctness risk is a missed invalidation showing stale data — so the review traces every write against the invalidation wiring.

Watch for: nothing blocking. One behavioral nuance (confirmed): on a cache hit the admin path in both pages now assigns the *shared* cached array instance to component state rather than a fresh fetch result; this is safe only as long as no downstream code mutates that array in place. The `createKeyedCache` helper is implemented and unit-tested but wired to no production fetch (confirmed dead-but-tested).

**Verdict**: APPROVED

## High-level view

The cache mechanism is a faithful extraction of the already-proven `ensureClubConfigCache` pattern: a module-level `Promise<T> | null`, populated once, shared by concurrent callers, with a `.catch` that resets the slot to `null` and re-throws so a failed fetch never poisons the cache. Behavior on the happy path is identical to pre-change; the only runtime difference is that an unchanged revisit skips a full re-page.

Every mutation that writes `accuracy_checks` or `accuracy_disputes` was traced against its invalidation. All twelve check mutations and all six dispute write-paths clear the correct caches, including the four cross-table check mutations (`deleteMaster`, `deleteAccuracyCheck`, `restoreAccuracyCheck`, `purgeAccuracyCheck`) that also clear GD/OC because those lists inner-join on the parent check's `deleted_at`. No write path is missing an invalidation. The two non-trivial placements — `propagateMasterCorrection` clearing M in a `finally` around its throwing loop, and `mergeMasters` clearing M right after Step 3 commits so a Step-4 throw can't leave M stale — both hold up.

The exported signatures are unchanged (`getAccuracyChecksMeta` and friends still return `Promise<T>`), so the two page callers are untouched and still `await` the getters. Scope stayed inside `accuracyChecks.ts`, `disputes.ts`, and the new `cache.ts` + `cache.test.ts`; no UI, engine, or schema files changed. Single-row and XML/blob fetches are deliberately left uncached. The cache helper's unit test exercises populate-once, concurrent-dedupe, invalidate-forces-refetch, and error-does-not-poison for both the single-value and keyed variants.

### Cache mechanism mirrors the proven clubConfig pattern

`createCache` extracts `ensureClubConfigCache`'s error path verbatim: the fetch's `.catch` resets `cache = null` before re-throwing, so a transient Supabase failure rejects the current callers and the next `get()` retries against a clean slot — a failed fetch never poisons the cache (confirmed against clubConfig's `loadMap().catch(...)`). This is the no-poisoning behavior the task requires (check item 4).

### Invalidation coverage — every write traced

Grepping both files for `.insert(` / `.update(` / `.delete(` and pairing each committed write with its `invalidate*` call confirms nothing was missed (all confirmed by reading the edited sources):

`accuracy_checks`: `saveAccuracyCheck` (insert) → M; `updateAccuracyCheck` (update) → M; `propagateMasterCorrection` (update loop) → M in `finally`; `renameMaster` (update) → M; `deleteMaster` (soft-delete) → M+D+GD+OC; `mergeMasters` (Step-3 update) → M; `fixStaleMasterTotals` (update loop) → M; `backfillPlayerAccuracy` (update loop) → M; `recomputeAllPlayerAccuracy` inherits via `backfillPlayerAccuracy`; `deleteAccuracyCheck` (soft-delete) → M+D+GD+OC; `restoreAccuracyCheck` (restore) → M+D+GD+OC; `purgeAccuracyCheck` (hard delete, CASCADE) → M+D+GD+OC.

`accuracy_disputes`: `createDispute` update/restore branch → GD+OC; `createDispute` insert branch → GD+OC; `createDispute` empty-patch early return writes nothing and correctly invalidates nothing; `resolveDispute` → GD+OC; `deleteDispute` → GD+OC; `restoreDispute` → GD+OC.

The four cross-table check mutations call `invalidateAllDisputesCache()` and `invalidateOpenDisputeCountsCache()` imported from `disputes.ts`. The import direction is one-way (`accuracyChecks → disputes`; `disputes.ts` imports only `@/lib/supabase` and `@/lib/api/cache`), so no cycle — consistent with the worktree `tsc --noEmit` PASS recorded in verification.md.

### Two non-trivial invalidation placements hold up

`propagateMasterCorrection`'s per-row loop throws on any `upErr`, so it can commit several rows and then throw mid-way. Clearing M in a `finally` wrapping the loop fires on both the normal return and a mid-loop throw after committed rows — so a partial propagation can't leave M showing pre-correction summaries. Confirmed by reading the restructured try/finally.

`mergeMasters` clears M immediately after Step 3's source-row re-tag commits, *before* the Step-4 re-grade. The reasoning that this one clear suffices is confirmed: nothing reads M between the clear and the function return, and Step 4 is resilient (per-row failures are logged and skipped, a `loadErr` throws). On every exit path the cache is already null, so the next read refetches — M cannot be left stale regardless of how Step 4 ends.

### Uncached fetches are the right ones

Single-row and XML/blob reads stay uncached (check item 3): `getAccuracyCheckById`, `getSavedMasterXml`, `getAccuracyChecksXml`, `getMasterCheckSiblings`, `getSavedMasters`, `diagnoseMasterConsistency`, `getDisputesForCheck`. Confirmed none are wrapped in `createCache`.

### Signatures unchanged, callers untouched, scope contained

The four getters changed from `async function (): Promise<T>` to `function (): Promise<T>` returning `cached.get()` — the external contract (`Promise<T>`) is identical, so the two consumers (`app/accuracy-checks/page.tsx`, `app/disputes/page.tsx`) still `await` them unchanged. `git diff --stat` shows only `accuracyChecks.ts` and `disputes.ts` among tracked code files, plus untracked `cache.ts`/`cache.test.ts`; no components, comparison engine, or schema touched.

### Shared-reference nuance on the admin path

On a cache hit `getAccuracyChecksMeta()` returns the same array instance to every caller. The admin branch does `setAllChecks(data)` / `setChecks(c)` with that instance (the analyst branch builds a new array via `filter`, so it's unaffected). Pre-change each call returned a fresh array, so this is a real behavioral delta (confirmed by reading both page fetch handlers). It is safe as long as nothing mutates the state array in place — the current consumers only `map`/`filter`/sort-into-new-arrays — but it's a latent footgun. A short "treat as read-only" comment on the fetch helpers would close the gap. Non-blocking: no current code path mutates in place.

### Cache helper test proves the risky mechanism

`cache.test.ts` drives both helpers with counting/throwing stub fetchers — no network. For `createCache`: populate-once (two sequential gets → one fetcher call, same resolved instance), concurrent-dedupe (two gets before resolve share one fetch), invalidate-forces-refetch, and error-does-not-poison (rejected fetch resets the slot, next get retries). For `createKeyedCache`: key isolation, key-normalization collapse, invalidate-clears-all, and per-key error-does-not-poison. This directly proves dedupe and invalidate-forces-refetch — the two properties the whole change relies on. Not tested: the data-module wiring itself (which `invalidate*` fires on which mutation) — that is verified by code review against the matrix rather than by an integration test, which is a reasonable split given the mutations require a live Supabase client.
